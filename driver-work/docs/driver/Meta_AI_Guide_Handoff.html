CHARACTER DRIVER / COORDINATION HANDOFF

What the definitive
Shadowveil HTML guide should establish

A handoff specification for the guide being prepared in Meta AI. This document is not the definitive guide and does not approve or redesign Shadowveil.

Core architecture: a hidden 3D driver controls layered 2D artwork. The final character stays illustrated. No finished shaded, textured, or sculpted 3D character is requested.

1. Keep the guide human-readable

Continue producing the explanatory HTML as planned. It does not need to become an application, a JSON-only document, or a 3D model. Use labeled images and explicit decisions. Unknown measurements should remain unknown rather than becoming invented canonical values.

2. Technical measurements are optional

If reliable measurements exist, annotate them with units and coordinate conventions. The pilot currently uses the old front registration only: 512 × 1100 bind pixels, origin (258.8, 527) in that image, X toward image-right, Y up, Z toward the front observer. Its initial Z values are zero, not an approved body-depth definition.

The final guide does not have to adopt those provisional measurements. Different units, ratios or a refined hierarchy can be described clearly and mapped during the next explicit calibration pass.

Do not fabricate hidden geometry. A front drawing does not establish shoulder depth, the back of a hand, or the underside of a raised arm. Identify those as art/registration requirements. The existing pilot's joint count is not a canonical limit on the future design.

3. Optional machine-readable appendix

An ordinary HTML guide can be imported as an archived reference. The following optional block helps retain its identity and revision. It is parsed as data, never executed. It does not automatically authorize rig changes.

<script type="application/json" id="character-driver-guide">
{
  "schema": "character-driver-guide/1",
  "characterId": "shadowveil",
  "revision": "replace-with-your-guide-revision",
  "notes": "Optional metadata. Do not invent missing measurements. No calibration is automatically applied."
}
</script>

Optional landmarks metadata can be added later with explicit units: "bind-pixels" and coordinates: "x-image-right_y-up_z-front". This foundation only recognizes existing driver IDs; unsupported formats are flagged rather than guessed. Leaving this block out is acceptable.

4. What happens after the guide arrives

The actual guide is imported and reviewed, then explicitly approved. Existing seed bindings are marked for re-registration—not silently fitted to different proportions. The driver calibration, artwork landmarks and numerical weights are then reviewed together.

The first art proof is 12 drawings: three neutral registration views, three anatomical-right-arm corrections, three open-palm replacements, and three concealed shoulder/underarm completions. They cover front, the character's right three-quarter and right profile. More art is commissioned/generated only after that mapping proof works.

5. What the current foundation does not claim

It does not automatically understand arbitrary interactive HTML, execute the guide's scripts, auto-fit anatomy, complete missing drawings, or approve weight maps from colored images. Full 3D IK, per-part multi-view selection, artist-authored corrective morphs and a finalized depth cage are subsequent engineering/asset stages.
